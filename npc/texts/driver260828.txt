    CPU实现硬件交互的purpose, 软硬件结构:
⭐ CPU -> 硬件接口API(IOE) -> 具体用这个接口的某个设备的驱动 -> 用户应用程序

⭐ 对于外设驱动 Driver 的理解:

硬件设备的驱动是在 硬件接口协议基础上的 更加specific的 软件协议

用串口举例, 两个同样用串口通信的设备, 他们在需要配置不同的 波特率 桢格式 时序协议(写成软体的更具体的时序) 等

层次	具体差异	例子
物理层	波特率、数据格式	9600 vs 115200
协议层	帧格式、命令结构、校验方式	NMEA 文本 vs 二进制命令帧
时序层	主动上报 vs 请求响应、延时要求	GPS 不等待 vs 温湿度需延时
语义层	数据怎么解释	"GPGGA" 字符串 vs 0x30 指令

所以, 我们在写裸机嵌入式程序时候, 要先:  配置复用引脚   config硬件接口   编写该接口软件逻辑   编写系统整体软件逻辑 
其中的 config硬件接口   编写该接口软件逻辑 其实就是在编写驱动(Driver)

      

	串口（UART）	PCIe 设备
连接方式	SoC 内部集成，永远存在	外部插槽，设备可能变化
地址分配	固定映射 (Fixed Mapping)	动态分配 (Dynamic Allocation)
分配时机	芯片设计时	系统启动时 (由 BIOS/OS 枚举)
目的	追求简单、低延迟、确定性	追求灵活、可扩展、节省资源
谁来分配	ASIC 设计者写死在硬件译码器里	OS 驱动根据设备 BAR 请求动态分配



⭐ 在CPU的视角来看, for RISCV, 比如我的0xa000f000-0xa000f0ff定义为一个USB接口, 固定映射, 这个在硬件里面写死
那OS怎么知道这个地址是USB接口地址呢?

这个API是 芯片厂 和 Linux内核的一套代码 来生成的
1.芯片厂提供 ⭐datasheet , 2.板厂把datasheet中的地址映射写成 ⭐设备树 文件并且load到板子上的Flash里面, (如果是设计SOC, 两部都要完成)
    3.然后首次启动OS的时候, OS会读取设备树文件, 生成对应的API代码

ASIC 设计者将地址映射固化在硅片上 → 通过数据手册和设备树将信息记录下来 → OS 启动时解析设备树 → 
    驱动程序从设备树中读取 reg 字段 → 驱动通过 ioremap 访问该地址 → 软件成功操作 USB 控制器。

层级	谁来做	产出物	作用
硬件层	ASIC Designer（你）	Verilog 代码 + 数据手册	定义硬件事实（地址 0xA000F000 是 USB）
软件抽象层	ASIC 的软件团队或 BSP 工程师	usb.h / usb_api.c	提供宏定义和基础 API 封装
OS 核心层	Linux/RTOS 内核开发者	通用 USB 子系统框架	提供驱动模型和注册机制
OS 适配层	芯片厂商的 Linux BSP 工程师	设备树文件 + usb_driver.c	将硬件信息（设备树）与 OS 驱动框架对接
